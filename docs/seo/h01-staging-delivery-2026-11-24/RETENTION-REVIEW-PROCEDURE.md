# Manual record-review checklist

26 November 2026. Expanded from the 24 November draft for KTK-team use. This delivery supplies the procedure and blank templates; it does not claim that a live review cycle has been performed. No automatic expiry, reminders, removal facility or customer communication is added.

## Start here

The KTK team already monitors `pubthroughkrakow@gmail.com`. A team member with the existing company-wide Customer Enquiries view/update permissions carries out the review. Use the [copyable note and private-index template](RECORD-REVIEW-TEMPLATE.md).

The review points are the end of the relevant purpose and a manual monthly check of due/unresolved items. These are review points, not storage-expiry periods. Choose the next actual review date for each retained or unresolved item. The checklist does not schedule a job or establish a universal retention period.

**This repository is public. Keep real enquiry references, Gmail links, identities, notes and review decisions in an existing KTK-restricted workspace. The repository template and worked cases contain no real records.** An actual private review index is not created by this delivery.

## Operator checklist

1. **Open the right workspace.** Use Customer Enquiries in OmniLodge and the KTK Chrome profile signed in to the intended Gmail mailbox. Verify the mailbox before opening a notification. If the controls or permissions differ from those below, stop and clarify the interface; do not grant access or guess an action.
2. **Define the review scope.** In OmniLodge use Form and Handling status, normally Closed, then work through the relevant pages. Keep a minimal private record of filters, pages covered and the last reference examined. Do not call a partial page scan a completed backlog review. Search covers name, email or subject, not internal notes or a review-due date. Use the restricted review index for due dates; there is no automatic due-date queue.
3. **Check why the data is still needed.** Open the exact record and verify its displayed reference. Check the submitted fields, notification and existing notes without copying their contents into another log. Review any ongoing request, recruitment, prize administration, actual obligation or active claim. Record unknown facts as unknown; do not turn a generic claims label into a reason to keep everything.
4. **Record one disposition.** Use `keep_for_specific_purpose`, `propose_removal` or `needs_case_decision` in the private review note/index. These are plain-text review labels, not new OmniLodge handling statuses. State the necessary retained scope and a brief reason. A retained, unresolved or proposed-removal item needs a responsible reviewer and next manual check date; an outstanding privacy request also needs response tracking.
5. **Save the review note carefully.** Read existing Internal notes and append a short entry, preserving earlier notes. Keep the handling status appropriate to the customer task; Closed does not erase data. Choose an existing active assignee if needed. Save follow-up once, reopen/read back the current note and intended status/assignment, and check Activity. On a conflict, preserve your new paragraph privately before Reload latest, then reconcile it with the latest notes. On an uncertain save, read back the row before trying again. Do not mark Replied merely because a review or Gmail opening occurred.
6. **Finish the review, not an unperformed removal.** A removal recommendation remains `proposed—not executed`. Prepare the exact scope below and route it to the responsible KTK operator for a reviewed technical action. Record what was actually checked and left open. Never label a privacy request or cross-system removal complete because one enquiry was closed, a note saved or a Gmail label changed.

## Review triggers by record group

| Record group | Start a review when | Check in particular |
| --- | --- | --- |
| Service enquiry without booking | The request is resolved, withdrawn or no longer pursued | Any specific continuing purpose; unnecessary full message copies |
| Enquiry linked to a booking or dispute | Handling ends or a relevant milestone changes | Necessary enquiry facts versus protected booking/transaction records; a specific hold if applicable |
| Job application | That recruitment process ends | Any separate justified arrangement for future recruitment; no automatic marketing enrolment |
| Competition entry | The relevant round or prize-administration purpose ends | Unsuccessful entries versus necessary winner/prize records; separate permission for story publication |
| Privacy/removal request | It arrives through any channel | Immediate routing and response tracking; do not wait for the monthly cycle |

Winner claim/redemption/accommodation instructions remain the owner's private email process after winner selection. This checklist reviews the records supporting that process; it does not reopen requests for public prize instructions or change following-month prize use.

## Requests from individuals take the priority route

Log the original receipt date and request scope promptly, assign a KTK handler and track the response date separately from the monthly review. The usual response requirement is prompt handling and, in principle, within one calendar month; do not substitute a 30-day counter or restart the clock when a record is opened. Escalate any proposed extension, exception or refusal for appropriate assessment within the applicable response period. This routine does not replace the team's existing enquiry-response commitments. [European Commission: handling requests](https://commission.europa.eu/law/law-topic/data-protection/information-business-and-organisations/dealing-requests-individuals_en).

Use additional identity information only when reasonably needed to resolve doubt, and use a proportionate check. Keep verification status/reference rather than copying identity documents into ordinary notes. Do not assume that every erasure request must be granted or refused automatically; relevant circumstances and exceptions require assessment. [EDPB: individual-rights workflow](https://www.edpb.europa.eu/sme/be-compliant/respect-individuals-rights_en).

A request arriving only in Gmail is logged in the restricted index; do not create a fake website submission to make it appear in OmniLodge. Historical Gmail import remains deliberately later. Earlier delivery-only rows can lack saved form contents; that is not proof of deletion. Use the existing Gmail link when present and verify the matching message in the correct account. Opening a message can mark it read normally, but does not send a reply. This preparation opens no messages and changes no mailbox flags.

## Exact-scope preparation for a proposed removal

- List the private references to the affected OmniLodge enquiry, submitted fields, immutable notification snapshot, current notes and audit metadata. Assess the necessary scope; do not edit around immutable-record or rollback guards.
- Identify the matching Gmail messages/attachments and any already-known exports or backup copies. A thread may contain unrelated material, so a whole-thread action is not automatically in scope. Do not start a new supplier, contract, location, hosting-account or billing investigation; those owner-discarded checks stay closed.
- Record any specific obligation/active-claim exception and the limited data it concerns. Protected booking/order/payment/accounting records and B03 originals, signed metadata, markers and recovery archives are outside this checklist's removal authority.
- Describe the reviewed technical method, access, restoration handling and verification for all known copies before carrying out any authorised disposal. The current Customer Enquiries feature supplies no erasure/anonymisation control. Do not use ad hoc SQL, bulk mailbox actions, template edits or a form resend as a shortcut.
- Record actual completion and any remaining exception only after the affected systems are checked. A missing cross-system method is an open technical action, not a completed removal. Escalation and planning must not become a reason to ignore an individual's response deadline.
